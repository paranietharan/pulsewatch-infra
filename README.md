## 🏗 Architecture Overview

PulseWatch runs on a cost-effective, high-availability AWS EKS setup:
- **EKS Cluster:** Kubernetes workloads distributed across AWS EC2 worker nodes.
- **Microservices:**
  - `api`: Go Chi HTTP backend API
  - `web`: Next.js 15 frontend dashboard
  - `scheduler`: Background monitor schedule evaluator
  - `probe-worker`: Distributed health check probes
  - `notification-service`: Alert dispatcher (Email/SMTP and webhooks)
  - `rabbitmq`: Message broker for real-time queueing
- **Database:** Managed Amazon RDS PostgreSQL instance.
- **Routing:** AWS Application Load Balancer (ALB) via AWS Load Balancer Controller.

## 🔐 Secrets Management (AWS Secrets Manager)

All sensitive credentials and environment configurations are securely stored in **AWS Secrets Manager**. Both the GitHub Actions CI/CD pipeline and the local deployment script (`scripts/deploy.sh`) automatically discover and inject these secrets into Kubernetes at deploy time.

### 1. Database Credentials
Provisioned automatically via Terraform:
- **Secret Name:** `pulsewatch-eks-rds-credentials`
- **JSON Structure:**
  ```json
  {
    "username": "pulsewatch_admin",
    "password": "<auto-generated-or-custom-db-password>"
  }
  ```

---

### 2. SMTP Credentials (Amazon SES or Custom SMTP)

Used by `pulsewatch-notification-service` to dispatch monitor downtime alerts and notification emails.

#### Production (`pulsewatch-prod-smtp-credentials`)
Create or update via AWS CLI:
```bash
aws secretsmanager create-secret \
  --name "pulsewatch-prod-smtp-credentials" \
  --region ap-south-1 \
  --description "SMTP credentials for PulseWatch Production" \
  --secret-string '{
    "user": "YOUR_PROD_SMTP_USER",
    "password": "YOUR_PROD_SMTP_PASSWORD",
    "host": "email-smtp.ap-south-1.amazonaws.com",
    "port": "587",
    "from": "PulseWatch <alerts@yourdomain.com>"
  }'
```
*(To update later, use `aws secretsmanager put-secret-value --secret-id "pulsewatch-prod-smtp-credentials" --region ap-south-1 --secret-string '...'`)*

#### Staging (`pulsewatch-staging-smtp-credentials`)
Create or update via AWS CLI:
```bash
aws secretsmanager create-secret \
  --name "pulsewatch-staging-smtp-credentials" \
  --region ap-south-1 \
  --description "SMTP credentials for PulseWatch Staging" \
  --secret-string '{
    "user": "YOUR_STAGING_SMTP_USER",
    "password": "YOUR_STAGING_SMTP_PASSWORD",
    "host": "email-smtp.ap-south-1.amazonaws.com",
    "port": "587",
    "from": "PulseWatch Staging <alerts-staging@yourdomain.com>"
  }'
```

---

### 3. JWT Secret (Authentication)

Used by `pulsewatch-api` to sign and verify user JWT authentication and session tokens.

#### Production (`pulsewatch-prod-jwt-secret`)
Generate a strong 64-character secret and store it:
```bash
# Generate a random 64-character secret
PROD_JWT_SECRET=$(openssl rand -hex 32)

aws secretsmanager create-secret \
  --name "pulsewatch-prod-jwt-secret" \
  --region ap-south-1 \
  --description "JWT signing secret for PulseWatch Production" \
  --secret-string "{\"secret\":\"$PROD_JWT_SECRET\"}"
```

#### Staging (`pulsewatch-staging-jwt-secret`)
```bash
STAGING_JWT_SECRET=$(openssl rand -hex 32)

aws secretsmanager create-secret \
  --name "pulsewatch-staging-jwt-secret" \
  --region ap-south-1 \
  --description "JWT signing secret for PulseWatch Staging" \
  --secret-string "{\"secret\":\"$STAGING_JWT_SECRET\"}"
```

*(Plaintext strings like `--secret-string "my-super-secret-key"` are also supported)*.

## ⚙ Alternative Secrets Configuration

If you prefer not to use AWS Secrets Manager, you can configure secrets through **GitHub Environment Secrets** or apply them directly to the Kubernetes cluster using `kubectl`.

### Option A: GitHub Environment Secrets
Set secrets scoped to the `production` or `staging` environment via GitHub CLI:

```bash
# Production
gh secret set SMTP_USER --env production -b "YOUR_SMTP_USER"
gh secret set SMTP_PASSWORD --env production -b "YOUR_SMTP_PASSWORD"
gh secret set SMTP_HOST --env production -b "email-smtp.ap-south-1.amazonaws.com"
gh secret set SMTP_PORT --env production -b "587"
gh secret set SMTP_FROM --env production -b "PulseWatch <alerts@yourdomain.com>"
gh secret set JWT_SECRET --env production -b "$(openssl rand -hex 32)"

# Staging
gh secret set SMTP_USER --env staging -b "YOUR_STAGING_SMTP_USER"
gh secret set SMTP_PASSWORD --env staging -b "YOUR_STAGING_SMTP_PASSWORD"
gh secret set SMTP_HOST --env staging -b "email-smtp.ap-south-1.amazonaws.com"
gh secret set SMTP_PORT --env staging -b "587"
gh secret set SMTP_FROM --env staging -b "PulseWatch Staging <alerts-staging@yourdomain.com>"
gh secret set JWT_SECRET --env staging -b "$(openssl rand -hex 32)"
```

### Option B: Direct Kubernetes Patch (`kubectl`)
Apply directly to live running pods for immediate effect:

```bash
# Production
kubectl -n production patch secret pulsewatch-production-secrets --type merge -p '{
  "stringData": {
    "SMTP_USER": "YOUR_PROD_SMTP_USER",
    "SMTP_PASSWORD": "YOUR_PROD_SMTP_PASSWORD",
    "JWT_SECRET": "YOUR_PROD_JWT_SECRET"
  }
}'
kubectl -n production patch configmap pulsewatch-production-config --type merge -p '{
  "data": {
    "SMTP_HOST": "email-smtp.ap-south-1.amazonaws.com",
    "SMTP_PORT": "587",
    "SMTP_FROM": "PulseWatch <alerts@yourdomain.com>"
  }
}'
kubectl -n production rollout restart deployment pulsewatch-production-notification-service pulsewatch-production-api

# Staging
kubectl -n staging patch secret pulsewatch-staging-secrets --type merge -p '{
  "stringData": {
    "SMTP_USER": "YOUR_STAGING_SMTP_USER",
    "SMTP_PASSWORD": "YOUR_STAGING_SMTP_PASSWORD",
    "JWT_SECRET": "YOUR_STAGING_JWT_SECRET"
  }
}'
kubectl -n staging patch configmap pulsewatch-staging-config --type merge -p '{
  "data": {
    "SMTP_HOST": "email-smtp.ap-south-1.amazonaws.com",
    "SMTP_PORT": "587",
    "SMTP_FROM": "PulseWatch Staging <alerts-staging@yourdomain.com>"
  }
}'
kubectl -n staging rollout restart deployment pulsewatch-staging-notification-service pulsewatch-staging-api
```

## 🚀 Deployment Workflows

### Automated Deployment (GitHub Actions)
Triggered from the main application repository (`paranietharan/pulsewatch`) via `.github/workflows/deploy.yml`:
- Builds and pushes microservice images to Amazon ECR.
- Automatically connects to AWS Secrets Manager to pull DB, SMTP, and JWT credentials.
- Checks out this repository's Helm chart (`pulsewatch-infra/helm/pulsewatch`).
- Runs `helm upgrade --install` with `--wait --timeout 10m`.

### Manual Local Deployment
Deploy directly from your machine using the helper script:

```bash
# 1. Connect kubectl to EKS
aws eks update-kubeconfig --region ap-south-1 --name pulsewatch-eks

# 2. Deploy to Staging
./scripts/deploy.sh staging

# 3. Deploy to Production
./scripts/deploy.sh production

# 4. Deploy with custom image tag
./scripts/deploy.sh production 01ad593
```

The script automatically fetches all secrets from AWS Secrets Manager before rolling out Helm.

## 🌐 Ingress & Cloudflare Domain Setup

Both namespaces expose an AWS Application Load Balancer (ALB):
- **Production ALB:** Ingress routes `/api` to `pulsewatch-production-api:8080` and `/` to `pulsewatch-production-web:80`.
- **Staging ALB:** Ingress routes `/api` to `pulsewatch-staging-api:8080` and `/` to `pulsewatch-staging-web:80`.

### Connecting Your Domain via Cloudflare:
1. In Cloudflare DNS:
   - Add a `CNAME` record pointing your domain (e.g. `app` or `@`) to the **Production ALB DNS Name**.
   - Add a `CNAME` record for `staging` pointing to the **Staging ALB DNS Name**.
   - Set **Proxy status** to **Proxied** (Orange Cloud).
2. In Cloudflare SSL/TLS:
   - Set encryption mode to **Flexible** (Cloudflare terminates HTTPS and communicates with AWS ALB over port 80).
